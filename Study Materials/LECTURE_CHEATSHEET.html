RECURSION
[-2pt] Key ideas: base case (immediate, obvious); recursive case calls self on smaller/similar problem; each call has own local vars on stack; must approach base case. Largest: compare head vs. largest(rest). Reverse: remove head, recurse, append head at end. Member-of: head==x OR member(rest). Multiply i×j: base j=0; else i + mult(i,j-1).
TOWERS OF HANOI
[-2pt]

Move n disks src→dst using tmp. Recursive solution:

  1. solve(n-1, src, dst, tmp) — move top n-1 via dst
  2. move(src→dst) — base case: 1 disk
  3. solve(n-1, tmp, src, dst) — move from tmp

Total moves: 2^n - 1. ``Very difficult without recursion!''  Pins swap roles (src/tmp/dst) each call.

FIBONACCI DISASTER
[-2pt] f(n)=f(n-1)+f(n-2): exponential redundant calls; bogs down. Use iteration instead. Recursion is powerful but use appropriately.
QUICKSORT (1961, ``most elegant'')
Partition: pick middle as pivot (A); park at right by swap (B); set i=left-1, j=right; loop until j crosses i: move i right while data[i] (C); move j left while data[j]>pivot (D); if i swap data[i],data[j] (E); swap pivot back in at i. Sort: base: size<2 return; size=2 swap if needed; else partition, recursively sort left &amp; right subarrays.
DYNAMIC BACKTRACKING
[-2pt]

Decision tree: try a path; backtrack on dead end; try next path. Base case = no further paths (dead end) or solution found. Can find all solutions by continuing after finding one.

N-Queens (8): solve column-by-column L→R. is\_safe\_position(row,col) checks left attacks. find\_solutions() recurses right. After each safe square, backtrack to try next. 92 solutions.
[-2pt] Sudoku: brute-force 1–9 per cell; L→R top→bottom; recursively check ahead; backtrack to next number after trying all 9; backtrack to previous cell.
MULTITHREADING
[-2pt] Thread: path through code; own stack+registers; shares code/data/resources. Concurrency (switch among tasks, 1 CPU) vs. Parallelism (simultaneous, multi-CPU). Shared resource: output stream, memory. Critical region: code accessing shared resource. Mutual exclusion: only 1 thread in critical region at a time.
mutex: lock() blocks if already locked; unlock() on exit. lock\_guard< mutex>: RAII — auto-locks on construct, auto-unlocks on scope exit; prevents deadlock from forgotten unlock. Context switching: runtime switches threads; this\_thread::yield() voluntary relinquish. this\_thread::sleep\_for(chrono::seconds(n)).
Reader-Writer: shared\_mutex. Writers use unique\_lock< shared\_mutex> (exclusive — no readers or writers). Readers use shared\_lock< shared\_mutex> (multiple readers OK; blocks writers).
atomic< T>: thread-safe without mutex; store(), load(), – ops.
condition\_variable: cv.wait(lock) — atomically unlocks+sleeps; re-locks when notified; always use while() loop (spurious wakeup). cv.notify\_all() wakes all waiting.
PRODUCER-CONSUMER
[-2pt]

Queue with capacity. Producers wait on producer\_cv when full (is\_full()). Consumers wait on consumer\_cv when empty (is\_empty()). Producer notifies consumers when just\_became\_not\_empty() (size==1). Consumer notifies producers when just\_became\_not\_full() (size==CAP-1). When all producers done, notify consumers.

Dining Philosophers: 5 philosophers, 5 chopsticks (one between each). Need both adjacent; must pick up both at once (cannot hold one and wait). Loop: think→wait→fill bowl→eat. Deadlock: all blocked; prevent with consistent lock ordering.
auto: type inference from initializer. decltype(x): yields type of variable x; use to declare same-type variable.

OOP DESIGN
[-2pt] Encapsulation: data+behavior in class; public/private; contains/isolates changes. Abstraction: ignore irrelevant details. Inheritance: subclass from superclass; adds/overrides state+behavior. Polymorphism: base ptr calls correct subclass method at runtime via virtual. dynamic\_cast< T*>(ptr): type-check+convert; returns nullptr if wrong type. Abstract class: ≥1 pure virtual (=0); cannot instantiate; subclasses must implement. Interface class: all pure virtual, no member vars. virtual destructor required if subclasses exist. Override (same signature, different class) vs. Overload (same name, different params, same scope).
Liskov Substitution (LSP): subclass substitutable for superclass. Violation: CircularBuffer:vector exposes invalid vector methods (at(), erase()); Fix: has-a not is-a (member vector buffer). Code to Interface: declare as base ptr, assign subclass at runtime.
DESIGN SMELLS

Principle of least surprise violation: Date MONTH\_NAMES[12] off-by-one (month=9→OCT not SEP). DRY violation: repeated code in multiple classes.

FUNCTORS (Function Objects)
[-2pt]

Class overloading operator()(). Stores state across calls in member vars. Can be stored, passed, returned. RandomInt ri(5,12); ri(); — next random int. Summation adder; adder(3); — accumulates sum. ()(){} syntax: first () = operator name, second () = params.

MOVE SEMANTICS &amp; BIG FIVE
[-2pt] lvalue: named variable (can be left of assignment). rvalue: temporary, about to be destroyed. Moving rvalue = ``steal'' resources O(1) vs copy O(n). std::move(x): force lvalue to behave as rvalue. Rule of Big Five: if define any one → define all: destructor, copy ctor, copy assign, move ctor, move assign. Move ctor/assign steal and set source to valid empty state (nullptr). Avoids costly copies of temporary objects (e.g., push\_back(first+" "+last)).
SMART POINTERS
[-2pt] Raw ptrs: memory leak risk, double delete, no ownership clarity. unique\_ptr< T>: exclusive ownership; auto-deleted on scope exit/reset; cannot copy (only move via std::move); source set to nullptr. shared\_ptr< T>: shared ownership via ref count; auto-deleted when count=0; copy increments count; reset() decrements; deleted exactly once.
VECTORS &amp; PERFORMANCE
[-2pt]

Growing copies all elements O(n). Use reserve() to pre-allocate. Store T* not T to avoid copy overhead on insert/remove (only pointer copies). Remove shifts all following elements.

TEMPLATE METHOD DP
[-2pt] Intent: fixed algorithm skeleton in base class (template method}); varying steps as abstract methods in subclasses. Structure: superclass (GameReport) has generate\_report() calling steps in order; implements common steps (print\_header/footer); abstract steps (acquire\_data, analyze\_data, print\_report) in subclasses (BaseballReport, VolleyballReport). Mechanism: Inheritance. Keywords: ``algorithm outline'', ``fixed sequence'', ``outline of steps''. vs. Strategy: TM=inheritance+fixed outline with varying steps; Strategy=composition+entire algorithm swapped.
STRATEGY DP
[-2pt] Intent: family of interchangeable algorithms; interface per family; concrete classes implement; context has-a strategy ptr set at runtime. Structure: Sport has player\_strategy and venue\_strategy ptrs to interfaces PlayerStrategy and VenueStrategy; concrete classes (BaseballPlayers, Stadium, OpenField) implement interfaces. Mechanism: Composition. Keywords: ``interchangeable'', ``runtime selection'', ``family of algorithms''. vs. TM: Strategy swaps entire algorithm; TM varies steps within fixed outline.
FACTORY METHOD DP
[-2pt] Intent: creator superclass has abstract factory method; subclass decides which product to instantiate. Structure: Creator=AthleticsDept; ConcreteCreators=VarsityDept, IntramuralDept; factory method=create\_sport(); Product=Sport. Superclass delegates object creation to subclasses. Mechanism: Inheritance. Keywords: ``subclass decides'', ``single product type'', ``factory method''. vs. Abstract Factory: FM=single product type; AF=families of related products; AF prevents mixing families.
ABSTRACT FACTORY DP
[-2pt] Intent: interface creates families of related objects; concrete factory creates one consistent family; prevents mixing families. Structure: AbstractFactory=ProvisionsFactory; ConcreteFactories=VarsityFactory, IntramuralFactory; each creates family (make\_players(), make\_venue()). Mechanism: Composition. Keywords: ``product family'', ``consistency'', ``prevents mixing''. vs. FM: AF ensures family consistency; FM just delegates single-type creation to subclass.
ADAPTER DP (Object)
[-2pt] Intent: make incompatible interfaces work together; wrap legacy/external code. Structure: Target interface (AttendanceData); Adapter (FootballData) implements Target + aggregates Adaptee (FootballInfo); converts calls. Class Adapter: uses multiple inheritance instead of aggregation; can override adaptee methods. Keywords: ``incompatible interface'', ``legacy code'', ``wrapper''. vs. Facade: Adapter=make incompatible work; Facade=simplify complex.
FACADE DP
[-2pt] Intent: simple high-level interface to complex subsystem; hide complexity. Structure: Facade class (FundRaiser) delegates to subsystem classes (Alumni, BoosterClubs, Students); clients (AthleticsDept, Administration) only call facade. Keywords: ``simplify'', ``hide complexity'', ``front door'', ``single interface''.
SINGLETON DP
[-2pt] Intent: exactly one instance; global access point. Structure: private constructor; private static ptr single\_instance; public static get\_singleton() — lazy creation (creates if null); deleted copy ctor+assign. Thread safety issue: multiple threads may each create instance if single\_instance==nullptr simultaneously. Keywords: ``one instance'', ``global access'', ``private constructor'', ``lazy construction''.
COMPOSITE DP
[-2pt] Intent: uniform treatment of leaf and composite; part-whole hierarchy. Structure: Component interface (ProvisionItem) + Leaf (e.g., Ball, Bat; no children) + Composite (ProvisionGroup: is-a ProvisionItem AND has-a vector< ProvisionItem*>); get\_cost() on composite sums children. Disable add/remove on leaves. Keywords: ``part-whole hierarchy'', ``tree structure'', ``recursive'', ``uniform treatment''.
DECORATOR DP
[-2pt] Intent: add responsibilities dynamically; flexible alternative to subclassing. Structure: Component=Ticket; ConcreteComponent=BaseTicket; Decorator abstract (is-a Ticket, has-a Ticket* to next); ConcreteDecorators=Party, VIP, Coupon; chain: get\_cost()=next->get\_cost()+my\_cost. Keywords: ``add responsibilities dynamically'', ``wrap'', ``chain''. vs. Composite: Decorator=single child+add behavior; Composite=multiple children+aggregate.
ITERATOR DP
[-2pt] Intent: traverse collection without exposing representation; decouple algorithm from collection type. Structure: Iterator interface (has\_next(), next()) + ConcreteIterators (ArrayIterator, VectorIterator, MapIterator) each with private cursor; Collection (Team subclasses) creates appropriate iterator; Client (TeamReport) uses only iterator interface. Note: C++ built-in iterators ≠ this pattern (not via common interface). Keywords: ``traverse'', ``decouple collection'', ``has\_next/next''.
VISITOR DP
[-2pt] Intent: add operations without modifying structure; different algorithms on single tree. Structure: Node interface has accept(Visitor&amp;); accept impl: v.visit\_X(this) then propagate to children; Visitor interface has visit\_NodeType() per type; ConcreteVisitors (ScoresReportVisitor, etc.) encapsulate algorithms. Double dispatch: node type + visitor type determine behavior. Analogy: craftsmen (painter, plumber) visiting rooms — each craftsman does different task per room type. Keywords: ``new operations'', ``node hierarchy'', ``double dispatch'', ``craftsmen visiting rooms''. vs. Iterator: Visitor=multiple algorithms on tree; Iterator=single traversal.
OBSERVER DP
[-2pt] Intent: publish-subscribe; 1-to-many; loose coupling. Structure: Subject has vector< Observer*> observers; subscribe/unsubscribe/notify() calls update() on each; Subject stores current\_event; Observer calls get\_current\_event() to pull data. BaseballReporter is Subject; LogReport, GraphReport, TableReport are Observers. Keywords: ``publish-subscribe'', ``notify'', ``1-to-many'', ``event-driven'', ``producer-consumer model''.
STATE DP
[-2pt] Intent: state-dependent behavior; object appears to change class; encapsulated transitions. Structure: Context (TicketMachine) has State* state member; delegates actions to current state. State interface has action methods. ConcreteStates (READY, VALIDATING, TICKET\_SOLD, SOLD\_OUT) encapsulate actions+transitions and return next State. StatesBlock aggregates all states (loose coupling). Each action fn returns next State*. UML state diagram documents transitions. Keywords: ``state-dependent behavior'', ``state machine'', ``encapsulated transitions'', ``alter behavior when state changes''.
