\hd{RECURSION}\\[-2pt]
\h{Key ideas:} base case (immediate, obvious); recursive case calls self on smaller/similar problem; each call has own local vars on stack; must approach base case. \h{Largest:} compare head vs.\ largest(rest). \h{Reverse:} remove head, recurse, append head at end. \h{Member-of:} head==x OR member(rest). \h{Multiply} $i{\times}j$: base $j{=}0$; else $i + \text{mult}(i,j{-}1)$.\\[-2pt]

\vspace{-1pt}\noindent\rule{\columnwidth}{0.2pt}\vspace{-3pt}

\hd{TOWERS OF HANOI}\\[-2pt]
Move $n$ disks src$\to$dst using tmp. Recursive solution:
\begin{enumerate}
  \item solve($n{-}1$, src, dst, tmp) — move top $n{-}1$ via dst
  \item move(src$\to$dst) — base case: 1 disk
  \item solve($n{-}1$, tmp, src, dst) — move from tmp
\end{enumerate}
Total moves: $2^n - 1$. ``Very difficult without recursion!''\quad Pins swap roles (src/tmp/dst) each call.\\[-2pt]

\vspace{-1pt}\noindent\rule{\columnwidth}{0.2pt}\vspace{-3pt}

\hd{FIBONACCI DISASTER}\\[-2pt]
\texttt{f(n)=f(n-1)+f(n-2)}: exponential redundant calls; bogs down. Use \h{iteration} instead. Recursion is powerful but use appropriately.\\[-2pt]

\vspace{-1pt}\noindent\rule{\columnwidth}{0.2pt}\vspace{-3pt}

\hd{QUICKSORT} (1961, ``most elegant'')\\[-2pt]
\h{Partition:} pick middle as pivot (A); park at right by swap (B); set \texttt{i=left-1, j=right}; loop until $j$ crosses $i$: move \texttt{i} right while \texttt{data[i]<pivot} (C); move \texttt{j} left while \texttt{data[j]>pivot} (D); if \texttt{i<j} swap \texttt{data[i],data[j]} (E); swap pivot back in at \texttt{i}. \h{Sort:} base: size$<$2 return; size$=$2 swap if needed; else partition, recursively sort left \& right subarrays.\\[-2pt]

\vspace{-1pt}\noindent\rule{\columnwidth}{0.2pt}\vspace{-3pt}

\hd{DYNAMIC BACKTRACKING}\\[-2pt]
Decision tree: try a path; backtrack on dead end; try next path. Base case = no further paths (dead end) or solution found. Can find all solutions by continuing after finding one.\\[-2pt]
\h{N-Queens (8):} solve column-by-column L$\to$R. \texttt{is\_safe\_position(row,col)} checks left attacks. \texttt{find\_solutions()} recurses right. After each safe square, backtrack to try next. \h{92 solutions.}\\[-2pt]
\h{Sudoku:} brute-force 1--9 per cell; L$\to$R top$\to$bottom; recursively check ahead; backtrack to next number after trying all 9; backtrack to previous cell.\\[-2pt]

\vspace{-1pt}\noindent\rule{\columnwidth}{0.2pt}\vspace{-3pt}

\hd{MULTITHREADING}\\[-2pt]
\h{Thread:} path through code; own stack+registers; shares code/data/resources. \h{Concurrency} (switch among tasks, 1 CPU) vs.\ \h{Parallelism} (simultaneous, multi-CPU). \h{Shared resource:} output stream, memory. \h{Critical region:} code accessing shared resource. \h{Mutual exclusion:} only 1 thread in critical region at a time.\\[-2pt]
\h{mutex:} \texttt{lock()} blocks if already locked; \texttt{unlock()} on exit. \h{lock\_guard\textless mutex\textgreater:} RAII — auto-locks on construct, auto-unlocks on scope exit; prevents deadlock from forgotten unlock. \h{Context switching:} runtime switches threads; \texttt{this\_thread::yield()} voluntary relinquish. \texttt{this\_thread::sleep\_for(chrono::seconds(n))}.\\[-2pt]
\h{Reader-Writer:} \texttt{shared\_mutex}. Writers use \texttt{unique\_lock\textless shared\_mutex\textgreater} (exclusive — no readers or writers). Readers use \texttt{shared\_lock\textless shared\_mutex\textgreater} (multiple readers OK; blocks writers).\\[-2pt]
\h{atomic\textless T\textgreater:} thread-safe without mutex; \texttt{store()}, \texttt{load()}, \texttt{--} ops.\\[-2pt]
\h{condition\_variable:} \texttt{cv.wait(lock)} — atomically unlocks+sleeps; re-locks when notified; always use \texttt{while()} loop (spurious wakeup). \texttt{cv.notify\_all()} wakes all waiting.\\[-2pt]

\hd{PRODUCER-CONSUMER}\\[-2pt]
Queue with capacity. Producers wait on \texttt{producer\_cv} when full (\texttt{is\_full()}). Consumers wait on \texttt{consumer\_cv} when empty (\texttt{is\_empty()}). Producer notifies consumers when \texttt{just\_became\_not\_empty()} (size==1). Consumer notifies producers when \texttt{just\_became\_not\_full()} (size==CAP-1). When all producers done, notify consumers.\\[-2pt]
\h{Dining Philosophers:} 5 philosophers, 5 chopsticks (one between each). Need both adjacent; must pick up both at once (cannot hold one and wait). Loop: think$\to$wait$\to$fill bowl$\to$eat. \h{Deadlock:} all blocked; prevent with consistent lock ordering.\\[-2pt]
\h{auto:} type inference from initializer. \h{decltype(x):} yields type of variable \texttt{x}; use to declare same-type variable.\\[-2pt]

\vspace{-1pt}\noindent\rule{\columnwidth}{0.2pt}\vspace{-3pt}

\hd{WELL-DESIGNED SOFTWARE}\\[-2pt]
Meets requirements \quad$\cdot$\quad Reliable (no surprises, no hidden perf issues) \quad$\cdot$\quad Flexible+scalable (add features without complexity) \quad$\cdot$\quad Maintainable \quad$\cdot$\quad Uses good design+patterns \quad$\cdot$\quad Saves time/cost. Design-code-test iterations (``Mozart'' analogy — iterative, not big-bang).\\[-2pt]

\vspace{-1pt}\noindent\rule{\columnwidth}{0.2pt}\vspace{-3pt}

\hd{OOP DESIGN}\\[-2pt]
\h{Encapsulation:} data+behavior in class; public/private; contains/isolates changes. \h{Abstraction:} ignore irrelevant details. \h{Inheritance:} subclass from superclass; adds/overrides state+behavior. \h{Polymorphism:} base ptr calls correct subclass method at runtime via \texttt{virtual}. \h{dynamic\_cast\textless T*\textgreater(ptr):} type-check+convert; returns \texttt{nullptr} if wrong type. \h{Abstract class:} $\geq$1 pure virtual (\texttt{=0}); cannot instantiate; subclasses must implement. \h{Interface class:} all pure virtual, no member vars. \h{virtual destructor} required if subclasses exist. \h{Override} (same signature, different class) vs.\ \h{Overload} (same name, different params, same scope).\\[-2pt]
\h{Liskov Substitution (LSP):} subclass substitutable for superclass. \h{Violation:} \texttt{CircularBuffer:vector} exposes invalid vector methods (\texttt{at()}, \texttt{erase()}); \h{Fix:} has-a not is-a (member \texttt{vector<int> buffer}). \h{Code to Interface:} declare as base ptr, assign subclass at runtime.\\[-2pt]

\vspace{-1pt}\noindent\rule{\columnwidth}{0.2pt}\vspace{-3pt}

\hd{DESIGN SMELLS}\\[-2pt]
\h{Leaking changes:} change in \texttt{Car} forces change in \texttt{Driver} (key$\to$button). \h{God class:} \texttt{AutomobileApp} — too many responsibilities (drive+maintain+wash). \h{Hardcoded concrete:} \texttt{Cat *pet = new Cat()}. \h{Principle of least surprise violation:} \texttt{Date} MONTH\_NAMES[12] off-by-one (month=9$\to$OCT not SEP). \h{DRY violation:} repeated code in multiple classes.\\[-2pt]

\hd{LAMBDA EXPRESSIONS}\\[-2pt]
Syntax: \texttt{[capture](params)->ret\{body\}}. No capture: \texttt{[](const T\& x)\{...\}}. Capture by ref: \texttt{[\&var]}; by value: \texttt{[var]}. \texttt{std::function\textless bool(const T\&)\textgreater} for lambdas with capture. \h{Predicate:} bool function whose return depends on params. Use with STL: \texttt{sort}, \texttt{find\_if}, etc. \texttt{auto f = [](int x)\{return x*2;\};}\\[-2pt]

\vspace{-1pt}\noindent\rule{\columnwidth}{0.2pt}\vspace{-3pt}

\hd{FUNCTORS (Function Objects)}\\[-2pt]
Class overloading \texttt{operator()()}. Stores state across calls in member vars. Can be stored, passed, returned. \texttt{RandomInt ri(5,12); ri();} — next random int. \texttt{Summation adder; adder(3);} — accumulates sum. \texttt{()(){}} syntax: first \texttt{()} = operator name, second \texttt{()} = params.\\[-2pt]

\columnbreak

\hd{MOVE SEMANTICS \& BIG FIVE}\\[-2pt]
\h{lvalue:} named variable (can be left of assignment). \h{rvalue:} temporary, about to be destroyed. Moving rvalue = ``steal'' resources O(1) vs copy O(n). \texttt{std::move(x):} force lvalue to behave as rvalue. \h{Rule of Big Five:} if define any one $\to$ define all: destructor, copy ctor, copy assign, move ctor, move assign. Move ctor/assign steal and set source to valid empty state (nullptr). Avoids costly copies of temporary objects (e.g., \texttt{push\_back(first+" "+last)}).\\[-2pt]

\vspace{-1pt}\noindent\rule{\columnwidth}{0.2pt}\vspace{-3pt}

\hd{SMART POINTERS}\\[-2pt]
\h{Raw ptrs:} memory leak risk, double delete, no ownership clarity. \h{unique\_ptr\textless T\textgreater:} exclusive ownership; auto-deleted on scope exit/reset; cannot copy (only move via \texttt{std::move}); source set to \texttt{nullptr}. \h{shared\_ptr\textless T\textgreater:} shared ownership via ref count; auto-deleted when count=0; copy increments count; \texttt{reset()} decrements; deleted exactly once.\\[-2pt]

\vspace{-1pt}\noindent\rule{\columnwidth}{0.2pt}\vspace{-3pt}

\hd{VECTORS \& PERFORMANCE}\\[-2pt]
Growing copies all elements O(n). Use \texttt{reserve()} to pre-allocate. Store \texttt{T*} not \texttt{T} to avoid copy overhead on insert/remove (only pointer copies). Remove shifts all following elements.\\[-2pt]

\vspace{-1pt}\noindent\rule{\columnwidth}{0.2pt}\vspace{-3pt}

\hd{MVC ARCHITECTURE}\\[-2pt]
\h{Model:} persistent data (memory/files/DB). \h{View:} UI components (fields, buttons, menus). \h{Controller:} coordinates model+view; dispatches user input to model. Qt6 framework; inversion of control; loose coupling among 3 types. User cannot directly modify model.\\[-2pt]

\hd{TEMPLATE METHOD DP}\\[-2pt]
\h{Intent:} fixed algorithm skeleton in base class (\emph{template method}); varying steps as abstract methods in subclasses. \h{Structure:} superclass (\texttt{GameReport}) has \texttt{generate\_report()} calling steps in order; implements common steps (\texttt{print\_header/footer}); abstract steps (\texttt{acquire\_data, analyze\_data, print\_report}) in subclasses (\texttt{BaseballReport, VolleyballReport}). \h{Mechanism:} Inheritance. \h{Keywords:} ``algorithm outline'', ``fixed sequence'', ``outline of steps''. \h{vs.\ Strategy:} TM=inheritance+fixed outline with varying steps; Strategy=composition+entire algorithm swapped.\\[-2pt]

\vspace{-1pt}\noindent\rule{\columnwidth}{0.2pt}\vspace{-3pt}

\hd{STRATEGY DP}\\[-2pt]
\h{Intent:} family of interchangeable algorithms; interface per family; concrete classes implement; context has-a strategy ptr set at runtime. \h{Structure:} \texttt{Sport} has \texttt{player\_strategy} and \texttt{venue\_strategy} ptrs to interfaces \texttt{PlayerStrategy} and \texttt{VenueStrategy}; concrete classes (\texttt{BaseballPlayers, Stadium, OpenField}) implement interfaces. \h{Mechanism:} Composition. \h{Keywords:} ``interchangeable'', ``runtime selection'', ``family of algorithms''. \h{vs.\ TM:} Strategy swaps entire algorithm; TM varies steps within fixed outline.\\[-2pt]

\vspace{-1pt}\noindent\rule{\columnwidth}{0.2pt}\vspace{-3pt}

\hd{FACTORY METHOD DP}\\[-2pt]
\h{Intent:} creator superclass has abstract factory method; subclass decides which product to instantiate. \h{Structure:} Creator=\texttt{AthleticsDept}; ConcreteCreators=\texttt{VarsityDept, IntramuralDept}; factory method=\texttt{create\_sport()}; Product=\texttt{Sport}. Superclass delegates object creation to subclasses. \h{Mechanism:} Inheritance. \h{Keywords:} ``subclass decides'', ``single product type'', ``factory method''. \h{vs.\ Abstract Factory:} FM=single product type; AF=families of related products; AF prevents mixing families.\\[-2pt]

\vspace{-1pt}\noindent\rule{\columnwidth}{0.2pt}\vspace{-3pt}

\hd{ABSTRACT FACTORY DP}\\[-2pt]
\h{Intent:} interface creates families of related objects; concrete factory creates one consistent family; prevents mixing families. \h{Structure:} AbstractFactory=\texttt{ProvisionsFactory}; ConcreteFactories=\texttt{VarsityFactory, IntramuralFactory}; each creates family (\texttt{make\_players(), make\_venue()}). \h{Mechanism:} Composition. \h{Keywords:} ``product family'', ``consistency'', ``prevents mixing''. \h{vs.\ FM:} AF ensures family consistency; FM just delegates single-type creation to subclass.\\[-2pt]

\vspace{-1pt}\noindent\rule{\columnwidth}{0.2pt}\vspace{-3pt}

\hd{ADAPTER DP (Object)}\\[-2pt]
\h{Intent:} make incompatible interfaces work together; wrap legacy/external code. \h{Structure:} Target interface (\texttt{AttendanceData}); Adapter (\texttt{FootballData}) implements Target + aggregates Adaptee (\texttt{FootballInfo}); converts calls. \h{Class Adapter:} uses multiple inheritance instead of aggregation; can override adaptee methods. \h{Keywords:} ``incompatible interface'', ``legacy code'', ``wrapper''. \h{vs.\ Facade:} Adapter=make incompatible work; Facade=simplify complex.\\[-2pt]

\vspace{-1pt}\noindent\rule{\columnwidth}{0.2pt}\vspace{-3pt}

\hd{FACADE DP}\\[-2pt]
\h{Intent:} simple high-level interface to complex subsystem; hide complexity. \h{Structure:} Facade class (\texttt{FundRaiser}) delegates to subsystem classes (\texttt{Alumni, BoosterClubs, Students}); clients (\texttt{AthleticsDept, Administration}) only call facade. \h{Keywords:} ``simplify'', ``hide complexity'', ``front door'', ``single interface''.\\[-2pt]

\vspace{-1pt}\noindent\rule{\columnwidth}{0.2pt}\vspace{-3pt}

\hd{SINGLETON DP}\\[-2pt]
\h{Intent:} exactly one instance; global access point. \h{Structure:} private constructor; private static ptr \texttt{single\_instance}; public static \texttt{get\_singleton()} — lazy creation (creates if null); deleted copy ctor+assign. \h{Thread safety issue:} multiple threads may each create instance if \texttt{single\_instance==nullptr} simultaneously. \h{Keywords:} ``one instance'', ``global access'', ``private constructor'', ``lazy construction''.\\[-2pt]

\vspace{-1pt}\noindent\rule{\columnwidth}{0.2pt}\vspace{-3pt}

\hd{COMPOSITE DP}\\[-2pt]
\h{Intent:} uniform treatment of leaf and composite; part-whole hierarchy. \h{Structure:} Component interface (\texttt{ProvisionItem}) + Leaf (e.g., \texttt{Ball, Bat}; no children) + Composite (\texttt{ProvisionGroup}: is-a \texttt{ProvisionItem} AND has-a \texttt{vector\textless ProvisionItem*\textgreater}); \texttt{get\_cost()} on composite sums children. Disable \texttt{add/remove} on leaves. \h{Keywords:} ``part-whole hierarchy'', ``tree structure'', ``recursive'', ``uniform treatment''.\\[-2pt]

\vspace{-1pt}\noindent\rule{\columnwidth}{0.2pt}\vspace{-3pt}

\hd{DECORATOR DP}\\[-2pt]
\h{Intent:} add responsibilities dynamically; flexible alternative to subclassing. \h{Structure:} Component=\texttt{Ticket}; ConcreteComponent=\texttt{BaseTicket}; Decorator abstract (is-a \texttt{Ticket}, has-a \texttt{Ticket*} to next); ConcreteDecorators=\texttt{Party, VIP, Coupon}; chain: \texttt{get\_cost()=next->get\_cost()+my\_cost}. \h{Keywords:} ``add responsibilities dynamically'', ``wrap'', ``chain''. \h{vs.\ Composite:} Decorator=single child+add behavior; Composite=multiple children+aggregate.\\[-2pt]

\vspace{-1pt}\noindent\rule{\columnwidth}{0.2pt}\vspace{-3pt}

\hd{ITERATOR DP}\\[-2pt]
\h{Intent:} traverse collection without exposing representation; decouple algorithm from collection type. \h{Structure:} Iterator interface (\texttt{has\_next(), next()}) + ConcreteIterators (\texttt{ArrayIterator, VectorIterator, MapIterator}) each with private cursor; Collection (\texttt{Team} subclasses) creates appropriate iterator; Client (\texttt{TeamReport}) uses only iterator interface. \h{Note:} C++ built-in iterators $\neq$ this pattern (not via common interface). \h{Keywords:} ``traverse'', ``decouple collection'', ``has\_next/next''.\\[-2pt]

\vspace{-1pt}\noindent\rule{\columnwidth}{0.2pt}\vspace{-3pt}

\hd{VISITOR DP}\\[-2pt]
\h{Intent:} add operations without modifying structure; different algorithms on single tree. \h{Structure:} Node interface has \texttt{accept(Visitor\&)}; \texttt{accept} impl: \texttt{v.visit\_X(this)} then propagate to children; Visitor interface has \texttt{visit\_NodeType()} per type; ConcreteVisitors (\texttt{ScoresReportVisitor}, etc.) encapsulate algorithms. \h{Double dispatch:} node type + visitor type determine behavior. \h{Analogy:} craftsmen (painter, plumber) visiting rooms — each craftsman does different task per room type. \h{Keywords:} ``new operations'', ``node hierarchy'', ``double dispatch'', ``craftsmen visiting rooms''. \h{vs.\ Iterator:} Visitor=multiple algorithms on tree; Iterator=single traversal.\\[-2pt]

\vspace{-1pt}\noindent\rule{\columnwidth}{0.2pt}\vspace{-3pt}

\hd{OBSERVER DP}\\[-2pt]
\h{Intent:} publish-subscribe; 1-to-many; loose coupling. \h{Structure:} Subject has \texttt{vector\textless Observer*\textgreater observers}; \texttt{subscribe/unsubscribe/notify()} calls \texttt{update()} on each; Subject stores \texttt{current\_event}; Observer calls \texttt{get\_current\_event()} to pull data. \texttt{BaseballReporter} is Subject; \texttt{LogReport, GraphReport, TableReport} are Observers. \h{Keywords:} ``publish-subscribe'', ``notify'', ``1-to-many'', ``event-driven'', ``producer-consumer model''.\\[-2pt]

\vspace{-1pt}\noindent\rule{\columnwidth}{0.2pt}\vspace{-3pt}

\hd{STATE DP}\\[-2pt]
\h{Intent:} state-dependent behavior; object appears to change class; encapsulated transitions. \h{Structure:} Context (\texttt{TicketMachine}) has \texttt{State* state} member; delegates actions to current state. State interface has action methods. ConcreteStates (\texttt{READY, VALIDATING, TICKET\_SOLD, SOLD\_OUT}) encapsulate actions+transitions and return next State. \texttt{StatesBlock} aggregates all states (loose coupling). Each action fn returns next \texttt{State*}. \h{UML state diagram} documents transitions. \h{Keywords:} ``state-dependent behavior'', ``state machine'', ``encapsulated transitions'', ``alter behavior when state changes''.\\[-2pt]
